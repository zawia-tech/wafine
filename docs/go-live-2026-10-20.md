# Go-live 2026-10-20: plan B runbook

Invite-only launch of WAFINE with **web and docs on the production hosts** and the **API on the playground API host**, which is already public through the Cloudflare Tunnel. The production API host (Cloudflare for SaaS, `terraform/cloudflare` custom hostnames, [15-launch-checklist.md](15-launch-checklist.md) option A) is switched on after the launch; nothing here touches Cloudflare.

Every hostname below is a placeholder. The real values live in the operator vault, never in this repo.

| Placeholder | Meaning |
|---|---|
| `app.example.com` | production web host (Vercel project `web`) |
| `docs.example.com` | production docs host (Vercel project `docs`) |
| `api.playground.example.com` | playground API host, the BFF behind the tunnel (plan B API) |
| `web.playground.example.com` | playground web host (same Vercel project `web`) |
| `example.com` | the DNS zone at the registrar (Namecheap) |
| `hello@example.com`, `no-reply@example.com` | contact mailbox and Auth sender on the zone |

Rules for the whole run: no step deletes data (owner rule: keep all data); migrations are only ever added; secrets come from `pass` and are typed into prompts, never pasted into chat, logs or git.

The smoke test used at every check is [`scripts/go-live-check`](../scripts/go-live-check):

```bash
WEB_URL=https://app.example.com API_URL=https://api.playground.example.com \
DOCS_URL=https://docs.example.com scripts/go-live-check
```

It prints `PASS|FAIL <check> <detail>` per line and exits 1 on any failure. Before step 1, run it against the playground web host to see today's baseline (web checks fail on the pre-rebrand build, `api-waitlist` fails with 404).

## 1. Database migrations (waitlist)

Applies all three pending migrations in one push: `20261017120000_waitlist`, `20261018120000_waitlist_status` and `20261018130000_openwa_strip_archived_media`. The owner moved media offload before launch (18/10/2026, the database was at 427 of 500 MB), so run this step inside the media sequence of `docs/11-media-storage.md`: after the OCI buckets, key and VM settings exist, and before the backfill. The dry run must list exactly these three.

```bash
cat supabase/.temp/project-ref          # must print the openwa-ma project ref (vault); stop otherwise
supabase db push --dry-run              # lists exactly the pending migrations, no error
supabase db push                        # owner only
supabase migration list --linked
```

`supabase db push` applies every pending local migration in order, so the dry run will usually list the media one too. Pushing it now is safe: its trigger only rewrites a row whose media already has a stored object (`mediaPath` set), which cannot happen before media offload is configured. If you prefer to hold it back, run the push from a checkout without that file and push it later; never edit an applied migration.

- **Expected:** both waitlist versions appear in the Remote column.
- **Check:** `supabase migration list --linked`.
- **Rollback:** none. The migrations only add a table, a column and policies; keep-all-data forbids dropping them, and an unused table is harmless. If the BFF misbehaves, roll the BFF back (step 3), not the schema.

## 2. Auth email through Brevo SMTP

Sign-up is email and password through Supabase Auth. Supabase's built-in mailer only delivers to members of the project's organization (about 2 mails per hour), so invited users would never receive their confirmation mail. The app itself sends no mail.

Supabase dashboard > Authentication > Emails > SMTP settings:

| Field | Value |
|---|---|
| Host | `smtp-relay.brevo.com` |
| Port | `587` |
| Username | Brevo SMTP login (lives in `pass`) |
| Password | Brevo SMTP key (lives in `pass`) |
| Sender email | `no-reply@example.com` |
| Sender name | `WAFINE` |

Then Authentication > Rate limits: raise "emails sent per hour" to cover the invite wave (custom SMTP starts at 30 per hour).

The sender domain must be the one already authenticated in Brevo (its DKIM CNAMEs and verification TXT are live on the zone): **no DNS record changes**, and the SPF record stays as it is. Brevo signs with DKIM, which is what DMARC aligns on.

Email templates: paste the WAFINE versions (Confirm signup, Invite user, Reset password) from the vault's invitation pack.

- **Expected:** a sign-up with an invited test address receives the confirmation mail from `no-reply@example.com` within a minute.
- **Check:** Brevo > Transactional > Logs shows "delivered"; Supabase > Logs > Auth shows no SMTP error.
- **Rollback:** switch "Enable custom SMTP" off (back to the built-in mailer). Nothing else changes.

## 3. Redeploy the API (BFF) from `main`

The live BFF predates the waitlist (`api-waitlist` returns 404). Deploy `main` first **without** changing `WEB_URL`, so Claude connectors keep their consent page until the web cutover in step 8.

```bash
git switch main && git pull --ff-only
ssh <vm> 'grep -cE "^(WEB_URL|PUBLIC_API_URL)=" /opt/wa/stack/.env'   # must print 2 (compose requires both)
scripts/deploy.sh
```

For plan B, `PUBLIC_API_URL` stays `https://api.playground.example.com` (it is the REST base and MCP URL shown to users).

- **Expected:** `/health/ready` 200 on the VM loopback; the waitlist route is mounted.
- **Check:** `ssh <vm> 'curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4000/health/ready'` prints 200, and `scripts/go-live-check` shows `PASS api-waitlist 400`, `PASS api-health`, `PASS api-auth-gate`, `PASS api-oauth`, `PASS api-mcp`.
- **Rollback:** `git switch --detach <commit from step 0> && ALLOW_ROLLBACK=1 scripts/deploy.sh` (deploys only move forward without the flag). The waitlist table stays.

## 4. Vercel domains

Add each production host to its project and read the DNS target Vercel assigns.

```bash
cd app/web  && vercel domains add app.example.com web --scope omnizya
cd app/docs && vercel domains add docs.example.com docs --scope omnizya
vercel domains inspect app.example.com --scope omnizya     # shows the CNAME target, and a _vercel TXT if needed
vercel domains inspect docs.example.com --scope omnizya
```

The dashboard path is Project > Settings > Domains > Add; it shows the same target.

- **Expected:** each domain is listed with an "Invalid configuration" warning until step 5, plus one CNAME target per host (form `<hash>.vercel-dns-0xx.com`).
- **Check:** `vercel domains ls --scope omnizya`.
- **Rollback:** `vercel domains rm app.example.com --scope omnizya` (and the docs host).

## 5. Registrar records (Namecheap, zone `example.com`)

Namecheap > Domain List > Manage > Advanced DNS > Add New Record, TTL Automatic. Host is relative to the zone.

| Type | Host | Value | When |
|---|---|---|---|
| CNAME | `app` (the web label) | web CNAME target from step 4 | always |
| CNAME | `docs` (the docs label) | docs CNAME target from step 4 | always |
| TXT | `_vercel` | verification value from step 4 | only if Vercel asks |

Change nothing else: apex, `www`, MX, SPF, DKIM, DMARC and the Brevo records stay untouched. No `api` record in plan B.

- **Expected:** both hosts resolve to the Vercel targets within about 30 minutes; Vercel marks both domains "Valid" and issues certificates.
- **Check:** `dig +short CNAME app.example.com`, `dig +short CNAME docs.example.com`, `dig +short MX example.com` (unchanged), `curl -sI https://example.com/ | head -1` (the zone's own site still answers).
- **Rollback:** delete the rows added here. Nothing else to restore.

Project `web`, Production environment. `NEXT_PUBLIC_*` values are inlined at build time, so they must exist before step 7. The build refuses to start without the first five (`app/web/src/lib/env-guard.ts`).

| Variable | Plan B value |
|---|---|
| `SITE_URL` | `https://app.example.com` |
| `NEXT_PUBLIC_API_URL` | `https://api.playground.example.com` |
| `NEXT_PUBLIC_DOCS_URL` | `https://docs.example.com` |
| `CONTACT_EMAIL` | `hello@example.com` |
| `NEXT_PUBLIC_CONTACT_EMAIL` | `hello@example.com` |
| `BFF_URL` (server-only, never `NEXT_PUBLIC_`) | `https://api.playground.example.com` |

```bash
vercel env rm SITE_URL production --scope omnizya --yes     # only for a name that already exists
vercel env add SITE_URL production --scope omnizya          # value typed at the prompt

vercel env ls production --scope omnizya
```

The playground web host is served by the same project, so its canonical URLs and OG tags will point at the production host too. That is intended.

- **Expected:** `vercel env ls production` lists all six names.
- **Check:** the build in step 7 passes the env guard.
- **Rollback:** restore the values from the step 0 snapshot (`vercel env rm` then `vercel env add`).

## Full rollback (five layers)

Run in this order; each layer is independent and can be rolled back alone.

1. **DNS:** delete the records added in step 5. The zone's own site and mail were never touched.
2. **Vercel:** `vercel rollback` to the step 0 deployments (web and docs); restore the env snapshot; remove the production domains (`vercel domains rm`).
3. **VM / BFF:** restore `/opt/wa/stack/.env` from `.env.bak-20261019`, `./stack/wa up -d`; if the new BFF itself is at fault, `ALLOW_ROLLBACK=1 scripts/deploy.sh` from the step 0 commit.
4. **Supabase Auth:** Site URL back to the playground web host; custom SMTP off only if it is the problem (otherwise keep it, the playground needs it too).
5. **Database:** nothing to undo. The waitlist migrations stay applied and their rows stay (keep all data).

Afterwards: tell the invited users, record the rollback and its cause in the vault journal.

Users who connected Claude to the playground MCP URL must reconnect.
